# 品播 GitHub 仓库管理规范 v1.0

## 一、三级结构
- GitHub 账号：个人身份 `weiyangnice`。
- Organization：未来公司技术资产的归属主体，需由负责人在 GitHub 创建并授权。
- Repository：一个可以独立管理生命周期的产品或复用组件。
- 目录：同一个仓库内部的代码、测试、文档和脚本。

## 二、业务分区（规划）
1. `pinbono-platform`：业务与生产流程中台。
2. `pinbono-ai-tools`：AI、素材与文案自动化。
3. `pinbono-website`：品牌官网、课程和商务落地页。
4. `pinbono-data-tools`：报表与数据处理。
5. `pinbono-templates`：成熟代码模板。
以上均为候选项目，按真实开发任务依次建立，不预先造空仓库。

## 三、命名标准
- 仓库：小写英文、用连字符分词，例如 `pinbono-ai-tools`。
- 分支：`feature/xxx`、`fix/xxx`、`docs/xxx`。
- 版本：遵循 `vMAJOR.MINOR.PATCH` 形式，例如 `v1.2.0`。
- 文档：业务解释可中文命名，便于搜索。
- Topics：`internal-tool`、`ai`、`website`、`automation`、`template`；避免在标签中放机密项目代号。

## 四、状态标准
- `proposed`：仅规划；
- `prototype`：原型验证；
- `active`：持续开发；
- `maintained`：稳定维护；
- `paused`：暂停；
- `archived`：归档。
状态写入 README，不依赖仓库名称堆叠“最新版”。

## 五、强制基础文件
每个正式项目应至少具备 README.md、.gitignore、.env.example（如有环境变量）、docs/ 和变更日志。面向团队协作的仓库还应提供 Issue / PR 模板和自动化测试。

## 六、协作与交付
- 代码变更建议先开分支，再开 PR，验证后合并。
- `main` 保存可用代码；重要仓库通过仓库规则保护分支。
- PR 至少说明改动原因、风险、测试方式、回滚方案。
- 发布使用 Release 和版本标签，不新建“最终版2”仓库。
- 交接原则：新接手者可以只读仓库说明完成启动、运行、部署、排障。

## 七、安全底线
- 公司业务代码与客户数据默认私有。
- 禁止提交密码、Token、密钥、.env、客户清单和原始商业视频。
- GitHub 主要管理代码及技术文档；Drive 管业务文档；NAS 管大体量影像资产。
- 最小权限分配；生产部署密钥应使用受控 Secrets 管理机制。
